Standalone, default off, not wired to product. With the user's existing scope and after independent review, only Leader executes it within the remaining troubleshooting budget. Every attempt counts: at most one GET of the selected account followed by at most one POST of the selected test page, no retry, redirect, proxy, account list, OAuth, Session, pagination, or version fallback. Two requests may consume two budget units, including failures. GET failure or invalid input prevents the POST. Each stage has a 15-second deadline and a 2 MiB response limit.

The [single-account API](https://docs.composio.dev/reference/api-reference/connected-accounts/getConnectedAccountsByNanoid.md) documents the `user_id` field as deprecated and says it may stop being returned. The runner obtains it only from the selected account's response in memory. The returned ID must match the selected account, `toolkit.slug` must be Notion, status ACTIVE, and both account and auth configuration disabled flags must be exactly false. Missing or invalid user ID, or any failed check, prevents the POST. No ID or user ID is printed or saved. This does not prove ownership, no fallback, token usability, or page permission.

The [REST execution schema](https://docs.composio.dev/reference/api-reference/tools/postToolsExecuteByToolSlug.md) lists `user_id`, account ID, version and arguments, without marking user_id required. The official SDK guide states a stronger user ID requirement; this is not proof of the REST error cause. Public search did not identify an authoritative meaning for code 1811. The observed `missing-user-id` hint is a keyword match, not a verified cause. POST fixes `NOTION_GET_PAGE_MARKDOWN`, version `20261101_00`, the same account, selected page ID and `include_transcript:false`; the in-memory GET user_id is added. The REST-only preview accepts `error:null` when `successful` is exactly true and the required object fields have valid types; it retains `schemaVerified:false`. No MCP response framing is inferred.

Only fixed status/shape, counts, a boolean indicating whether a usable user ID was present, and prior bounded page diagnostics are printed. No raw responses, errors, markdown, credentials, OAuth, account IDs or user IDs are printed or saved. The optional marker must be a user-approved non-sensitive test string.
